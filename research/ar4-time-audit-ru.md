## 5. Диагноз: что именно тормозит

Каждое утверждение — со ссылкой на факт из разделов 2–4 или из кода.

### Пайплайн (устройство)

**П-1. Харнесс суда — «чёрный ящик до конца».**
- Задачи в `eval/phenomena.py` идут в порядке агент → строка → группа → сид.
- Печать и сохранение — только в самом конце (`print` после `pmap`, лог процесса 29 мин
  показывал одну строку со временем старта).

Следствия:
- (а) задержка информации равна полной длительности прогона: 30–60 мин на решение;
- (б) остановка прогона теряет всё (D-20 в AR-2, h1 в D-36);
- (в) нет ни раннего ответа «по одному сиду на все строки», ни ранней остановки по
  безнадёжности.

Это главная причина 57 % ожидания: мне *нечего было читать*, пока прогон шёл.

**П-2. Длинные прогоны занимают оба CPU, и для проб места нет.**
- По умолчанию `pmap` берёт `os.cpu_count()` процессов.
- В 14:09–14:39 и 14:44–15:17 оба CPU были заняты длинными прогонами. Любая проба шла бы
  в конкуренции, замедляя суд и искажая его замер времени. Поэтому я ждал.
- После 14:39 я разделил «1 + 1», но второй CPU отдал *ещё одному длинному прогону* (D-37),
  а не пробам.

**П-3. Нет снимка кода на прогон.**
- Цепочка `a && b && c` запускает новый python на каждом шаге и подхватывает текущий код.
- Я правил `factor.py` под идущей цепочкой (D-36). Потом пришлось руками доказывать, что
  выход не изменился.
- Нет манифеста прогона: хеш кода, команда, время, число CPU. Этот аудит пришлось
  восстанавливать по mtime.

**П-4. Диагностические инструменты живут вне репозитория и пишутся заново.**
- `dbg_factor.py`, `dbg_sev.py`, `d3_weights.py`, `an_judge.py` лежат в `.cache/s3/`. Каталог
  в `.gitignore` и **исключён из снимков**, то есть между сессиями эти файлы могут пропасть.
- Это отдельные кодовые пути с собственными ошибками:
  - словарь проб в `dbg_factor.py` перезаписывал BX пробой BY;
  - `probe_t2` требует точных ключей строк (`renewal-aab` → KeyError);
  - `--worlds` без `--set` → KeyError;
  - первая проба `-C-V-X` была невалидна, потому что q не считалось в view-ветке. Ошибка
    модели нашлась случайно.

**П-5. Нет реестра результатов и эталонов.**
- Для каждого парного сравнения я руками искал файл эталона: `t1d3.json` против
  `t1d2_decompw.json`, где агент лежит в `summary`, `table` или `rows`.
- Каждый раз руками проверял совпадение сидов и шагов, каждый раз писал новый скрипт.

**П-6. Метрики без шкалы шума.**
- Вердикты T2 у порога (SR-sessions +.078) и GC на мирах с малым gap (d3: −.043 GC ≈ .001
  nats на канал) решают приёмку.
- Суд даёт точный ответ на вопрос, который частично есть шум. Это обесценивает дорогие
  прогоны.

**П-7. Правила, создающие простой.**
- «Отчёт не раньше 16:53» при готовом отчёте дало 8 мин `sleep`.
- «Длинные прогоны не позже 16:08» — разумно, но в сочетании с П-1 последний час пригоден
  только для проб. Это сработало хорошо *только потому*, что в 16:28 освободились оба CPU.

## 7. Направления решений (не реализовано, для обсуждения)

Принцип безопасности: **никаких новых параллельных путей вычисления того же числа.**
- Короткий тест должен быть *префиксом* суда, той же функцией на тех же сидах, а не
  отдельным скриптом.
- Каждое изменение харнесса проверяется побитовым совпадением с текущим выходом на малой
  конфигурации. Культура fingerprint в проекте уже есть.

1. **Суд «в любой момент»** (против П-1, без нового кода вычислений).
   - Порядок задач — по сидам (сид 0 по всем строкам и мирам, затем сид 1, …).
   - Каждая завершённая задача сразу дописывается в jsonl.
   - Сводка считается той же функцией из jsonl.
   - Прогон можно продолжить после остановки: готовые задачи пропускаются.

   Что даёт:
   - ответ «сид 0 на всё» через ≈ 1/16 длительности суда;
   - прерывание без потерь;
   - раннюю остановку **только для решения «бросить»** (безнадёжность). Приёмка — строго
     на пре-регистрированном N, иначе optional stopping раздувает ошибки.

   Риск ошибок низкий: задачи независимы, у каждой свой сид. Проверка — побитовое
   совпадение итоговой сводки со старым харнессом.
2. **Приоритет CPU вместо раздела** (против П-2).
   - Суды запускать с `nice -n 19`, пробы — с обычным приоритетом.
   - CPU не простаивает, пробы идут на полной скорости, суд просто замедляется на время проб.
   - Цена: замер времени внутри суда искажается. Цена — критерий 3b, поэтому её мерить
     отдельно и изолированно (это и так правило).
3. **Снимок кода и манифест на каждый прогон** (против П-3).
   - Запуск из копии `development/` в каталоге прогона.
   - Манифест: хеш, команда, время старта и конца, CPU.
   - Класс ошибок «правка под цепочкой» исчезает. Аудиты вроде этого становятся точными.
4. **Трассировка как часть модели и харнесса** (против П-4).
   - У модели метод `trace()` (слоты, веса членов, апостериоры места и режима, рождения).
   - У харнесса — флаг `--trace row,seed`.
   - Это одна кодовая база в репозитории с тестами, вместо одноразовых скриптов в `.cache`.
5. **Реестр результатов и один инструмент парного сравнения** (против П-5).
   - Индекс (набор, агент, сиды, шаги, файл, манифест).
   - Сравнение само проверяет совпадение сидов и шагов.
6. **Ступени в протоколе** (против М-1).
   - смоук: сид 0, все наборы, 3–5 мин, без пре-рега, утверждений не даёт;
   - затем dev: 4 сида, только целевые строки;
   - затем суд: пре-рег, 16 сидов.

   Пре-рег суда пишется только после смоука, который прошёл по направлению все целевые
   строки. Смоук одновременно даёт изолированную оценку времени (против М-4).
7. **Шкала шума к метрикам** (против П-6).
   - Реестр хрупких строк: эффект и разброс по всем моделям.
   - Для T1 — gap в nats рядом с GC.
   - Изменение критериев — только с пользователем.
8. **Очередь работы без CPU** (против М-3). При пре-реге суда сразу записать, что делаю,
   пока он идёт: дизайн следующего шага, проверка идентифицируемости, тесты.
9. **Финальное окно** (против П-7). Отчёт можно писать раньше как черновик в цикле. Правило
   «стоп только по времени» уже защищает от досрочного стопа, и `sleep` тогда не нужен.
   Предлагаю обсудить: исходная причина правила (досрочный стоп AR-3) реальна, менять его
   без вас не буду.

Порядок по отдаче: **1 → 2 → 6 → 3 → 4**, затем 5, 7, 8, 9. Пункты 1 и 2 вместе, по моей
оценке, убирают большую часть «ожидания» из раздела 3. Это оценка, а не измерение.
